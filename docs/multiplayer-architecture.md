# Multiplayer Architecture and Milestones

## Authority and protocol

The host is authoritative for shared world state. Clients send intentions; the host validates them and performs the world mutation. Clients do not apply unconfirmed world changes. Approved changes carry an event identity or state revision so duplicate delivery is idempotent.

Use a versioned, strongly typed protocol over transport-specific boundaries. Direct IP uses length-prefixed TCP over numeric IPv4 for handshake, session control, scene changes, and initial roster/pose snapshots. Frequent movement snapshots use small UDP datagrams with an independent sequence stream and a random per-connection 128-bit token issued over TCP. The host validates the sender against its ready TCP peer, token, scene, pose bounds, sequence, rate, and movement distance before relaying. The UDP path is confirmed over TCP; if it cannot be established or times out, movement falls back to TCP. TCP does not retransmit or queue stale UDP poses. Both sockets use the same numeric port (one TCP listener and one UDP listener), so internet firewall and router rules must permit both protocols. The design does not depend on Steam or provide discovery. Socket polling and packet handling run on Unity's main thread; DNS/connect setup is asynchronous for TCP, and UDP send/receive is non-blocking.

TCP currently carries all control data reliably. If a future transport sends frequent movement unreliably, movement must use an independent sequence stream. Snapshot transfers should be bounded and chunked. Start with four total players including the host. The BepInEx configuration allows a higher requested cap, but support beyond four must wait for replication and load validation.

## Sessions, identity, and synchronization

Direct IP connections have no trusted account identity. Each player enters a local display name in F8; BepInEx persists it in that installation's config, the versioned hello carries it, and the host rejects duplicate names within a session. The host roster carries player IDs and names for display. Session peer IDs remain random and session-scoped; names are user-selected labels, not authenticated credentials or safe persistent identity keys. Unity's game saves remain under the Windows user's `persistentDataPath`; the player name does not redirect TS2's own save files. Session phases are `Offline`, `Connecting`, `Handshaking`, `LoadingScene`, `ReceivingSnapshot`, `Ready`, and `Closing`. Normal replication starts only after a compatible peer has loaded the expected scene and applied its initial authoritative snapshot.

For static objects, prefer a verified game-owned ID. If none exists, derive an ID from a scene/build identity, canonical hierarchy path, and component discriminator; detect collisions and reject an ambiguous mapping with a diagnostic. Dynamic objects receive host-assigned IDs. Scene identity/version mismatch must fail synchronization instead of mapping objects by runtime instance ID or traversal order.

Remote player movement is snapshot-based and interpolated. Reuse a suitable existing full-body NPC model only after verifying the prefab. Remote representations must not run local input, camera, first-person hands, player UI, or save systems. Discrete actions and interactions use host-validated events.

### Remote-player lifecycle

Network peer identity is session-owned and survives scene transitions; a `RemotePlayerAvatar` is only a scene-owned visual. `RemotePlayerManager` maintains an authoritative roster view and latest pose cache, then runs one idempotent reconciliation path after roster, pose, readiness, and relevant scene events. It creates an avatar only when the peer is rostered, a matching-scene pose exists, and the local world is ready. Scene unload destroys scene objects without treating it as peer disconnect. Unity destroyed-object null semantics are checked before reuse, and stale-scene poses are discarded. A host scene transition invalidates cached peer poses so the old scene's last position cannot be used as a new-scene snapshot. Valid world poses received before client initial synchronization completes are held and replayed after synchronization. There is no timed spawn retry or per-frame reconciliation.

The previous manager spawned only from `PlayerPoseReceived`; `RosterChanged` only removed entries. Consequently a peer re-added after host scene synchronization could remain invisible until another accepted pose callback happened to arrive. The provided logs do not contain the menu-to-game transition, so they do not independently prove this was the observed run's exact trigger. The code path establishes the lifecycle ordering weakness; reproduce the menu path after deployment to confirm the fix in-game.

## Save and progression boundary

The host loads and saves the shared world through the existing game save system. Direct IP currently provides only random session peer IDs; persistent player state needs a host-approved stable credential, not an IP address or connection slot. Joining clients receive host world state through a session-scoped adapter; local client profiles must not become authoritative or be overwritten. Save integration must be gated on proving that host state can be staged/applied without changing the client's persistent save. If the existing `SPrefs`/profile flow cannot provide that boundary safely, stop before implementing persistence and document the required design choice.

Treat mission/story/time/world state as host-owned. Audit money, player inventory, and upgrades before deciding their persistence ownership. Host-approved capability changes should affect clients for the session without purchasing or permanently modifying a joining client's progression.

## Milestones and acceptance checks

1. **Foundation (implemented):** plugin bootstrap, configuration, logging, Harmony lifecycle, and these game findings. Build against the installed assemblies; verify plugin startup and shutdown without stale patches. Remove the placeholder per-attack logging patch.
2. **Direct IP connectivity (implemented; runtime pairing still required):** IPv4 TCP host/join, framed reliable transport, peer handshake, timeout and version errors. Verify two PCs on a LAN, incompatible version rejection, disconnect, and host shutdown. Internet sessions need a user-configured firewall/port-forward rule; automatic discovery and relay are not implemented. The initial transport has no encryption or peer authentication; keep it to trusted peers until that hardening is implemented.
3. **Local multi-instance test harness (launcher implemented; runtime validation and game-save isolation remain):** F8 player names are saved in BepInEx config and exchanged in the handshake and authoritative roster; the host rejects duplicates. Startup role/address/port config supports automatic host/client startup. `scripts/launch-local-session.ps1` deploys the plugin, stages isolated per-instance configs under `%LOCALAPPDATA%\StolenPlayer\LocalInstances`, assigns unique names, and starts one host plus one to three clients; `-StageOnly` prepares files without launching. The game data and BepInEx code are shared through junctions, while logs and configs are per instance. All processes still use the current Windows user's Unity `persistentDataPath`, so the harness is limited to connection and movement checks. Do not save or test progression with it. Verify repeatable startup, config/name separation, clean shutdown, and protocol behavior in the running game before treating the milestone complete.
4. **Remote players (first visual replication and event-driven lifecycle reconciliation implemented; reconnect regression fix deployed for verification):** serialized asset inspection identified `level1`'s `NPCs/101/NPC` as a full-body legacy-Animation candidate. The clone is staged inactive and stripped of gameplay components before activation. The avatar uses Unity's legacy `Animation` component, not Mecanim `Animator`; idle selection uses configurable exact names, with defaults preferring `Idle`, then `BreatheIdle`, then fallback idle states. Idle and movement clips play normally with looping and crossfades; no frozen-frame sampling is used. Position snapshots are sent at 10 Hz over UDP after a per-peer path is confirmed over TCP, and relayed by the host; TCP remains the fallback and carries initial poses/rosters. The host applies basic bounds, scene, rate, and movement-distance checks to incoming poses. On handshake, the host sends its active scene; the client loads it, receives the host pose and roster, moves its local controller beside the host, and only then starts movement replication. Player Y uses the CharacterController bounds bottom so the NPC feet align with the ground. Scene/spawn synchronization has an absolute 120-second failure deadline in addition to liveness heartbeats. Host broadcasts use roster revisions to abort stale batches if a send failure synchronously disconnects a peer. The 2026-10-09 launcher log showed first-join avatar creation succeeding, then reconnect avatar creation failing on both machines because the scene NPC template was no longer loaded. The plugin now preserves a sanitized inactive visual template in `DontDestroyOnLoad` after the first successful clone and uses it for later spawns/reconnects. Session identities are random and unauthenticated, so this is for trusted-peer visual prototyping only; these positions must not authorize interactions, AI, or persistence. The protocol supports at most four players. The temporary F9 scanner was removed after confirming the model; F10 remains a local-only preview. Lifecycle recreation is driven by roster/pose/readiness/scene events and avoids timed retry hacks. Manually verify menu connection before gameplay, late join, connected scene transition, repeated transitions, disconnect/reconnect, movement, animation, and leave cleanup. The fallback path, WAN port forwarding, and loss behavior still need multi-machine runtime validation.
5. **Interactions (ordinary door request and state replication implemented; runtime verification required):** a pure `StableObjectKey` builder derives a deterministic 128-bit key from product/version, scene identity, canonical hierarchy path, and component type; a local registry rejects duplicate path mappings and detects hash collisions by comparing full canonical inputs. The runtime scanner logs per-scene key-set fingerprints. In launcher run `Run-20261009-085758`, the host and client matched exactly: `MainScene` (`Assets/Sceny/MainScene.unity`) contained 16 doors with SHA-256 `EC9C67AC8CF2B50B942122016B2DE6134B602B668ABF432967A95FCF762AE691`, and `MadisonSt` (`Assets/Sceny/MadisonSt.unity`) contained 1,142 doors with SHA-256 `F378EDA3A766E3763822B4D84E94A7A8DFE89E63A1078F56F27AAC11B648F932`. This verifies matching static key sets for those two loaded scenes; it does not prove every scene, dynamic objects, or additive duplicate-scene behavior. The adapter intercepts `Door.Use()` and the `Door.load_slow` threshold on clients, sends a versioned reliable toggle intent, and applies only host-approved open/closed state. Intent and state messages preserve the normal/slow mode; slow transitions use TS2's `openingSlowly` path and speed progression on both peers. A 250 ms per-door guard suppresses duplicate callbacks from one slow interaction without imposing a multi-second lockout. The host requires a scene-ready peer, pose age <=1.25 seconds, matching active world scene, a standard unlocked pedestrian door, and 2.75 m range. It applies the transition without calling `Door.Use()` on behalf of a remote player, then reliably broadcasts the result. The packet scene is the active world scene (not the door component's additive scene), while the stable key identifies the actual door object. Unsupported locked/special doors are blocked on clients. Ordinary static doors are included in the late-join snapshot; lockpick, key, padlock, alarms, noise attribution, pickups, and other persistent world state remain unsynchronized. Door IDs are covered by host/client fingerprints for `MainScene` and `MadisonSt` only; other scenes still need identity verification. Focused protocol tests cover door payload round trips and malformed action/length/scene data. Manual acceptance: host and client ready in one scene; verify both normal and held-slow open/close transitions from either peer and confirm matching animations; attempt an unsupported locked/special door and confirm it produces no client-side world mutation; inspect logs for accepted state changes and stale/out-of-range rejects. Do not save progression in the multi-instance harness. Pickup requests originate in the local player's raycast/input branch; depending on pickup type and path, the coroutine can mutate inventory, carry weight, money/XP, missions/story, and destroy the object through game-local references with no target-peer parameter. A pickup adapter must follow a per-player inventory/save boundary rather than award the host on a client's request. Verify simultaneous pickup requests produce one result, while stale/invalid requests are rejected. See `game-architecture.md` for method-level findings.
6. **World state (ordinary door snapshot added; runtime validation required):** clients receive a count-checked host snapshot of supported ordinary doors before initial synchronization completes. Next add and validate other persistent world state, spawn/despawn, scene transitions, and pickups only after inventory authority is resolved. Verify late join after doors changed and ensure clients remain gated until snapshot completion.
7. **Persistence:** add a host-approved stable player credential and host-owned save behavior only after the save audit. Verify reconnect ownership, disconnect while carrying an item, and host save/reload without duplication or loss.
8. **Gameplay systems:** add AI, police, alarms, missions, vehicles, time, and remaining systems incrementally. Verify host authority for each system before expanding scope.
9. **Hardening:** test malformed packets, timeout, reconnect, scene mismatch, identity collisions, host shutdown, desync recovery, performance, and compatibility. Do not advance a milestone while duplication or persistent desynchronization remains.
