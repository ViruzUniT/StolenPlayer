# Multiplayer Architecture and Milestones

## Authority and protocol

The host is authoritative for shared world state. Clients send intentions; the host validates them and performs the world mutation. Clients do not apply unconfirmed world changes. Approved changes carry an event identity or state revision so duplicate delivery is idempotent.

Use a versioned, strongly typed protocol over a transport interface. The current transport is length-prefixed TCP over numeric IPv4 addresses; it does not depend on Steam or perform discovery. Include protocol version, message kind, per-session peer identity, object identity where relevant, and sequence/tick data. Bound message sizes (initial maximum: 64 KiB); reject incompatible handshakes and disconnect peers that send malformed or oversized frames. Ignore or reject stale request sequences. Socket polling and packet handling run on Unity's main thread; connection establishment is asynchronous. TCP provides ordered reliable delivery for the current control messages. A future movement transport can add unreliable delivery behind the same boundary.

TCP currently carries all control data reliably. If a future transport sends frequent movement unreliably, movement must use an independent sequence stream. Snapshot transfers should be bounded and chunked. Start with four total players including the host. The BepInEx configuration allows a higher requested cap, but support beyond four must wait for replication and load validation.

## Sessions, identity, and synchronization

Direct IP connections have no trusted account identity. The current handshake assigns a random session peer identity only; it is not persistent and does not authenticate a remote person. Add a host-approved player credential before storing persistent player data or exposing the listener to untrusted networks. Session phases are `Offline`, `Connecting`, `Handshaking`, `LoadingScene`, `ReceivingSnapshot`, `Ready`, and `Closing`. Normal replication starts only after a compatible peer has loaded the expected scene and applied its initial authoritative snapshot.

For static objects, prefer a verified game-owned ID. If none exists, derive an ID from a scene/build identity, canonical hierarchy path, and component discriminator; detect collisions and reject an ambiguous mapping with a diagnostic. Dynamic objects receive host-assigned IDs. Scene identity/version mismatch must fail synchronization instead of mapping objects by runtime instance ID or traversal order.

Remote player movement is snapshot-based and interpolated. Reuse a suitable existing full-body NPC model only after verifying the prefab. Remote representations must not run local input, camera, first-person hands, player UI, or save systems. Discrete actions and interactions use host-validated events.

## Save and progression boundary

The host loads and saves the shared world through the existing game save system. Direct IP currently provides only random session peer IDs; persistent player state needs a host-approved stable credential, not an IP address or connection slot. Joining clients receive host world state through a session-scoped adapter; local client profiles must not become authoritative or be overwritten. Save integration must be gated on proving that host state can be staged/applied without changing the client's persistent save. If the existing `SPrefs`/profile flow cannot provide that boundary safely, stop before implementing persistence and document the required design choice.

Treat mission/story/time/world state as host-owned. Audit money, player inventory, and upgrades before deciding their persistence ownership. Host-approved capability changes should affect clients for the session without purchasing or permanently modifying a joining client's progression.

## Milestones and acceptance checks

1. **Foundation (implemented):** plugin bootstrap, configuration, logging, Harmony lifecycle, and these game findings. Build against the installed assemblies; verify plugin startup and shutdown without stale patches. Remove the placeholder per-attack logging patch.
2. **Direct IP connectivity (implemented; runtime pairing still required):** IPv4 TCP host/join, framed reliable transport, peer handshake, timeout and version errors. Verify two PCs on a LAN, incompatible version rejection, disconnect, and host shutdown. Internet sessions need a user-configured firewall/port-forward rule; automatic discovery and relay are not implemented. The initial transport has no encryption or peer authentication; keep it to trusted peers until that hardening is implemented.
3. **Local multi-instance test harness:** automate deployment, isolated test identities and save/profile paths, and a launcher that starts one host plus a configurable number of clients. Verify repeatable host-plus-N startup, no profile/config collisions, clean shutdown, and protocol behavior.
4. **Remote players (first visual replication pass implemented; runtime pairing required):** serialized asset inspection identified `level1`'s `NPCs/101/NPC` as a full-body legacy-Animation candidate. The clone is staged inactive and stripped of gameplay components before activation. It prefers a neutral/standing idle if present, otherwise plays `StandUp` once and holds the final upright frame with `ClampForever`; `Bored` is the final fallback. Movement uses looping `Walk` and `Running` clips. Position snapshots are sent at 10 Hz over reliable TCP and relayed by the host; the host applies basic bounds, scene, rate, and movement-distance checks. On handshake, the host sends its active scene; the client loads it, receives the host pose and roster, moves its local controller beside the host, and only then starts movement replication. Player Y uses the CharacterController bounds bottom so the NPC feet align with the ground. Scene/spawn synchronization has an absolute 120-second failure deadline in addition to liveness heartbeats. Host broadcasts use roster revisions to abort stale batches if a send failure synchronously disconnects a peer. Session identities are random and unauthenticated, so this is for trusted-peer visual prototyping only; these positions must not authorize interactions, AI, or persistence. The protocol supports at most four players. The temporary F9 scanner was removed after confirming the model; F10 remains a local-only preview. Manually verify host plus clients see movement, animation, and leave cleanup. Reliable TCP can queue stale poses under congestion; replace with coalesced/unreliable movement delivery before treating this as a performance-hardened movement channel.
5. **Interactions (identity groundwork implemented; action audit underway):** a pure `StableObjectKey` builder derives a deterministic 128-bit key from product/version, scene identity, canonical hierarchy path, and component type; a local registry rejects duplicate path mappings and detects hash collisions by comparing full canonical inputs. A scene-load scanner indexes all in-scene `Door` components and logs ambiguous mappings. It currently uses a coarse product/version build identity, includes runtime-created doors present at scan time, and cannot distinguish two simultaneously loaded copies of the same scene; keys are not yet carried in network messages or safe to authorize replication. Tests cover deterministic identity, component/scene/build separation, required inputs, registry reuse, and duplicate rejection; no true SHA-256 collision is forced in tests. `PlayerScript.Update()` raycasts and handles door prompts/relocking/slow-open setup, but its ordinary door branch does not call `Door.Use()`; `SimplePlayerUse.RaycastCheck()` only handles the separate `SimpleOpenClose` demo component, so the normal door-open entry point remains unresolved. `Door.Use()` mutates door animation/state and its attached local player's movement/camera/noise state, while lock/key validation is not inside that method; `UseFully()` bypasses use gates and is used by vehicle code. Before a door adapter is implemented, trace the game callback that opens a standard door and determine how to validate locks on the host. Pickup requests originate in the local player's raycast/input branch; depending on pickup type and path, the coroutine can mutate inventory, carry weight, money/XP, missions/story, and destroy the object through game-local references with no target-peer parameter. A pickup adapter must follow a per-player inventory/save boundary rather than award the host on a client's request. Verify simultaneous pickup requests produce one result, while stale/invalid requests are rejected. See `game-architecture.md` for method-level findings.
6. **World state:** snapshots, scene transitions, and spawn/despawn. Verify a late join sees already-opened doors and already-collected items, and clients remain gated until snapshot completion.
7. **Persistence:** add a host-approved stable player credential and host-owned save behavior only after the save audit. Verify reconnect ownership, disconnect while carrying an item, and host save/reload without duplication or loss.
8. **Gameplay systems:** add AI, police, alarms, missions, vehicles, time, and remaining systems incrementally. Verify host authority for each system before expanding scope.
9. **Hardening:** test malformed packets, timeout, reconnect, scene mismatch, identity collisions, host shutdown, desync recovery, performance, and compatibility. Do not advance a milestone while duplication or persistent desynchronization remains.
